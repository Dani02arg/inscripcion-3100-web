GUIA DETALLADA DE AUTENTICACION Y PERFIL
========================================

Esta guia complementa guia-auth.txt; no la reemplaza.

Base URL local: http://localhost:8000
Prefijo de la API: /api

Las rutas protegidas requieren el JWT recibido al iniciar sesion:

Authorization: Bearer <token>
Content-Type: application/json
Accept: application/json

Las respuestas de ejemplo muestran la estructura. Los valores, identificadores
y fechas dependen de cada usuario. Los campos con valor null se omiten en los
recursos de usuario.

FLUJO SUGERIDO
--------------

1. Registrar el usuario.
2. Verificar el correo con el codigo recibido.
3. Iniciar sesion y guardar el token de forma segura.
4. Completar el perfil del tutor.
5. Consultar el perfil con GET /api/auth/me cuando sea necesario.
6. Al cerrar sesion, eliminar el token guardado en el cliente.

Todos los endpoints de esta guia
--------------------------------

Metodo  Endpoint                         Token
POST    /api/auth/register               No
POST    /api/auth/verify-email           No
POST    /api/auth/resend-code            No
POST    /api/auth/login                  No
POST    /api/auth/forgot-password        No
POST    /api/auth/reset-password         No
GET     /api/auth/me                     Si
POST    /api/auth/logout                 Si
PUT     /api/profile/tutor               Si (solo TUTOR)
POST    /api/role-request                Si

1. REGISTRAR USUARIO
--------------------

POST /api/auth/register

Que hace:
Crea una cuenta nueva con rol TUTOR y genera un codigo para verificar el
correo. La contrasena debe tener al menos 8 caracteres. La fecha de nacimiento
debe usar el formato YYYY-MM-DD. DNI, CUIL y correo deben ser unicos.

Envio:

{
  "dni": "30123456",
  "cuil": "20301234567",
  "name": "Ana",
  "lastname": "Perez",
  "email": "ana@example.com",
  "password": "ClaveSegura123",
  "user_phone": "3871234567",
  "birthdate": "1990-01-15"
}

Todos los campos del ejemplo son obligatorios. DNI y CUIL admiten hasta 20
caracteres; nombre y apellido, hasta 100; el telefono, hasta 20. El correo
debe tener formato valido y no estar registrado.

Respuesta exitosa: HTTP 201

{
  "data": {
    "id": "uuid-del-usuario",
    "name": "Ana",
    "lastname": "Perez",
    "email": "ana@example.com",
    "role": "TUTOR",
    "user_phone": "3871234567",
    "birthdate": "1990-01-15",
    "created_at": "2026-11-02T18:30:00+00:00",
    "updated_at": "2026-11-02T18:30:00+00:00"
  },
  "message": "Usuario registrado correctamente. Revisa tu correo para verificar tu cuenta."
}

El codigo no se devuelve en el JSON. Se envia por notificacion si
APP_SEND_NOTIFICATIONS esta habilitado. DNI, CUIL y contrasena no se incluyen
en la respuesta. occupation y education_level aun no aparecen porque no se
completaron.

Errores habituales:
- HTTP 422: datos invalidos, por ejemplo correo/DNI/CUIL ya registrados,
  fecha con formato incorrecto o campos obligatorios ausentes.
- Para errores de validacion, la respuesta incluye message y errors por campo.

2. VERIFICAR CORREO
-------------------

POST /api/auth/verify-email

Que hace:
Verifica el codigo de 5 digitos asociado al usuario y marca su correo como
verificado. Es necesario antes de iniciar sesion.

Envio:

{
  "user_id": "uuid-del-usuario",
  "code": "01234"
}

Respuesta exitosa: HTTP 200

{
  "message": "Correo verificado correctamente."
}

Errores habituales:
- HTTP 422: usuario o codigo invalidos, codigo vencido, usado o incorrecto.

3. REENVIAR CODIGO
------------------

POST /api/auth/resend-code

Que hace:
Solicita el envio de otro codigo para una cuenta existente. El servidor limita
los reenvios a 5 por dia y aplica un tiempo de espera de 45 segundos entre
envios. El codigo vence a los 15 minutos.

Envio aceptado por la validacion actual:

{
  "email": "ana@example.com",
  "type": "REGISTRAR"
}

El campo type acepta actualmente REGISTRAR o RECUPERAR.

Respuesta exitosa: HTTP 200

{
  "message": "Código reenviado correctamente."
}

Errores habituales:
- HTTP 422: email o tipo no validos, limite diario excedido o aun debe esperar.
- La respuesta contiene message con la causa. Si APP_SEND_NOTIFICATIONS esta
  deshabilitado, no se envia el correo aunque la operacion responda correctamente.

IMPORTANTE: hay una discrepancia en la implementacion actual. La validacion de
esta ruta acepta REGISTRAR/RECUPERAR, pero los flujos que verifican los codigos
usan internamente REGISTER/RECOVER. Por eso un codigo reenviado con esta ruta
puede no ser aceptado luego por verify-email o reset-password. Ademas, como el
servicio solo envia la notificacion de verificacion cuando el tipo es REGISTER,
los valores aceptados por esta ruta seleccionan la notificacion de recuperacion.
Revisar estas discrepancias antes de depender del reenvio en el frontend.

4. INICIAR SESION
-----------------

POST /api/auth/login

Que hace:
Comprueba email y contrasena. Solo permite iniciar sesion si el correo esta
verificado. Devuelve un JWT; su duracion predeterminada es de 24 horas y puede
configurarse con JWT_EXPIRATION.

Envio:

{
  "email": "ana@example.com",
  "password": "ClaveSegura123"
}

Respuesta exitosa: HTTP 200

{
  "data": {
    "token": "<jwt>",
    "user": {
      "id": "uuid-del-usuario",
      "name": "Ana",
      "lastname": "Perez",
      "email": "ana@example.com",
      "role": "TUTOR",
      "user_phone": "3871234567",
      "birthdate": "1990-01-15",
      "email_verified_at": "2026-11-02T18:30:00+00:00",
      "created_at": "2026-11-02T18:30:00+00:00",
      "updated_at": "2026-11-02T18:30:00+00:00"
    }
  },
  "message": "Inicio de sesión exitoso."
}

El objeto user puede incluir occupation y education_level cuando ya se hayan
completado. Los valores null se omiten.

Errores habituales:
- HTTP 401: credenciales invalidas o correo aun no verificado.
- HTTP 422: email/password ausentes o email con formato invalido.

5. SOLICITAR RECUPERACION DE CONTRASENA
---------------------------------------

POST /api/auth/forgot-password

Que hace:
Genera un codigo de recuperacion de 5 digitos y lo envia al correo registrado.
El codigo vence a los 15 minutos.

Envio:

{
  "email": "ana@example.com"
}

Respuesta exitosa: HTTP 200

{
  "message": "Se ha enviado un código de recuperación a tu correo."
}

Errores habituales:
- HTTP 422: email ausente, invalido o no registrado.
- El codigo no se incluye en la respuesta; se envia por notificacion si
  APP_SEND_NOTIFICATIONS esta habilitado.

6. RESTABLECER CONTRASENA
-------------------------

POST /api/auth/reset-password

Que hace:
Comprueba el codigo de recuperacion y, si es valido, cambia la contrasena.
La nueva contrasena debe tener al menos 8 caracteres y coincidir con su
confirmacion.

Envio:

{
  "email": "ana@example.com",
  "code": "01234",
  "password": "NuevaClave123",
  "password_confirmation": "NuevaClave123"
}

Respuesta exitosa: HTTP 200

{
  "message": "Contraseña restablecida correctamente."
}

Errores habituales:
- HTTP 422: codigo invalido, vencido o usado; email no registrado; contrasena
  ausente, menor a 8 caracteres o confirmacion distinta.

7. CONSULTAR USUARIO AUTENTICADO
--------------------------------

GET /api/auth/me

Que hace:
Devuelve el perfil del usuario identificado por el JWT. El frontend hace esta
solicitud autenticada y el backend devuelve los datos actuales del usuario.
Puede usarse, por ejemplo, para mostrar o verificar el perfil despues de
completarlo.

Envio:

GET /api/auth/me
Authorization: Bearer <jwt>

No requiere body.

Respuesta exitosa: HTTP 200

{
  "data": {
    "id": "uuid-del-usuario",
    "name": "Ana",
    "lastname": "Perez",
    "email": "ana@example.com",
    "role": "TUTOR",
    "user_phone": "3871234567",
    "birthdate": "1990-01-15",
    "occupation": "Docente",
    "education_level": "UNIVERSITARIO",
    "email_verified_at": "2026-11-02T18:30:00+00:00",
    "created_at": "2026-11-02T18:30:00+00:00",
    "updated_at": "2026-11-02T18:30:00+00:00"
  },
  "message": "Usuario autenticado."
}

El recurso no devuelve DNI, CUIL ni contrasena. Los campos que aun sean null
se omiten.

Errores habituales:
- HTTP 401: falta el token, es invalido/vencido o el usuario ya no existe.

8. CERRAR SESION
----------------

POST /api/auth/logout

Que hace:
Confirma el cierre de sesion. La autenticacion JWT es stateless: esta ruta no
revoca el token en el servidor. El cliente debe eliminar el token almacenado;
de lo contrario, seguira siendo valido hasta su vencimiento.

Envio:

POST /api/auth/logout
Authorization: Bearer <jwt>

No requiere body.

Respuesta exitosa: HTTP 200

{
  "message": "Sesión cerrada correctamente."
}

Error habitual:
- HTTP 401: falta el token o no es valido.

9. COMPLETAR O ACTUALIZAR PERFIL DE TUTOR
-----------------------------------------

PUT /api/profile/tutor

Que hace:
Guarda o actualiza la ocupacion y el nivel de estudios del usuario con rol
TUTOR. Ambos campos son obligatorios en cada solicitud.

Envio:

PUT /api/profile/tutor
Authorization: Bearer <jwt>
Content-Type: application/json

{
  "occupation": "Docente",
  "education_level": "UNIVERSITARIO"
}

Valores permitidos para education_level:
- PRIMARIO
- SECUNDARIO
- TERCIARIO
- UNIVERSITARIO
- POSTGRADO

occupation acepta texto de hasta 100 caracteres.

Respuesta exitosa: HTTP 200

{
  "data": {
    "id": "uuid-del-usuario",
    "name": "Ana",
    "lastname": "Perez",
    "email": "ana@example.com",
    "role": "TUTOR",
    "user_phone": "3871234567",
    "birthdate": "1990-01-15",
    "occupation": "Docente",
    "education_level": "UNIVERSITARIO",
    "email_verified_at": "2026-11-02T18:30:00+00:00",
    "created_at": "2026-11-02T18:30:00+00:00",
    "updated_at": "2026-11-02T18:30:00+00:00"
  },
  "message": "Perfil actualizado correctamente."
}

Errores habituales:
- HTTP 401: falta un JWT valido.
- HTTP 403: el usuario autenticado no tiene rol TUTOR.
- HTTP 422: falta algun campo, occupation supera 100 caracteres o
  education_level no pertenece a la lista permitida.

No hay un campo separado "es tutor responsable" en este endpoint. El perfil
solo solicita occupation y education_level; el tipo de usuario se expresa con
el rol TUTOR. Aunque existe middleware para comprobar que estos campos esten
completos, actualmente su alias no esta aplicado a rutas en routes/api.php.

10. SOLICITAR CAMBIO DE ROL
---------------------------

POST /api/role-request

Que hace:
Recibe el rol solicitado y el motivo. El usuario debe estar autenticado.

Envio:

{
  "requested_role": "ADMINISTRATIVO",
  "reason": "Necesito gestionar las inscripciones de la institucion."
}

requested_role acepta TUTOR, ADMINISTRATIVO o ADMINISTRADOR. reason es
obligatorio y admite hasta 500 caracteres.

Respuesta exitosa: HTTP 200

{
  "message": "Solicitud de cambio de rol enviada correctamente."
}

Errores habituales:
- HTTP 401: falta un JWT valido.
- HTTP 403: un usuario ADMINISTRADOR no puede solicitar cambio de rol.
- HTTP 422: rol invalido o faltan datos/se excede el largo permitido del motivo.

Alcance actual: el controlador valida y devuelve la confirmacion, pero indica
que el envio de notificaciones a administradores se implementaria despues.
Actualmente no persiste la solicitud ni cambia el rol del usuario.

FORMATO GENERAL DE ERRORES
--------------------------

Los errores de validacion suelen responder HTTP 422 con los campos message y
errors. Por ejemplo:

{
  "message": "The given data was invalid.",
  "errors": {
    "email": [
      "El correo electrónico no es válido."
    ]
  }
}

Las rutas protegidas responden HTTP 401 cuando falta un token o este no es
valido. En los ejemplos de esta guia no se muestran datos sensibles reales.
